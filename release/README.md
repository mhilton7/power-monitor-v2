# Release evidence directory

Release assets are generated by GitHub Actions from a clean tagged checkout. This directory contains policy and operator-readable notes only; test, migration, security, SBOM, provenance, image-digest, and Compose artifacts are attached to the corresponding GitHub release.

The checked-in TrueNAS production template is intentionally non-deployable until the release workflow substitutes registry-reported digests. A stable release is prohibited while any required automated gate fails or physical hardware certification is pending. Until actual marked hardware completes the hardware-in-loop suite, publish prerelease/release-candidate artifacts only.

Before creating server tag `v0.1.0-rc.27`, create, publish, and verify the exact
coordinated firmware prerelease metadata for `v0.1.0-rc.27`, including the
server tag and generated OpenAPI SHA-256 binding. Then set repository variable
`COMPATIBLE_FIRMWARE_TAG` to exactly `v0.1.0-rc.27`. Release gates fetch that
public firmware release, verify every checksum, require the `firmware.bin`
attestation, and validate its manifest, compatibility record,
host/fault/simulation report, and explicit pending physical status. Firmware
`v0.1.0-rc.25` is immutable historical evidence and must not be moved,
rewritten, or relabeled as RC26. Firmware RC17 is also immutable: its public
compatibility record omitted the telemetry contract binding, so no coordinated
server RC17 release was created. RC18 established the stateless architecture;
RC20 repairs null legacy-storage and acknowledgement compatibility. RC21 fixes
fixed-cadence sensor delivery and removes brown missing-period chart shading while retaining authenticated control under
`pm-protocol/1.0.0` and adds independently accepted current readings under
`pm-telemetry/2.0.0`. RC26 keeps that stateless runtime and advances the
coordinated firmware build number to 29.

Server `v0.1.0-rc.18` remains a public, immutable, installable prerelease with
its complete attached asset set. Hardware execution has confirmed that firmware
rc.1 through rc.5 crash in the main stack before provisioning. Do not move or
rewrite those historical releases. Later candidates carry that evidence
forward only through their own distinct tags, images, manifests, and release
assets. The signed server `v0.1.0-rc.22` tag is immutable failed-candidate
evidence: run
[`32451170213`](https://github.com/mhilton7/power-monitor-v2/actions/runs/32451170213)
passed mandatory gates, image publication, and anonymous GHCR verification,
then failed deterministic deployment smoke because a published bill-derived
day-sensitive rate required a holiday calendar that was not present. Release
assembly was skipped, so server RC22 has no GitHub Release or generated YAML.
Server RC25 is an immutable public prerelease. This source tree does not claim
that server RC26 has been published before its tagged workflow completes.

The valid signed server `v0.1.0-rc.4` tag is immutable historical evidence.
Its workflow job named `Mandatory release gates`, four image publications, and
anonymous GHCR checks passed,
but deterministic deployment smoke failed when Compose dependency traversal
restarted the already-completed initializer. Assembly was skipped, so rc.4 has
no server GitHub Release or generated release YAML and is not installable.

A source checkout intentionally has no generated release digests. Do not set
the compatibility variable to a local path, create an unsigned tag, treat local
Docker image IDs as GHCR digests, or replace the intentional `UNPUBLISHED_*`
sentinels by hand. The tagged workflows and the resulting public evidence are
the authority for whether a release exists.
